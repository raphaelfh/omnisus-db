# Rust DBF Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking. Delegação não é necessária para este plano.

**Goal:** Acrescentar um parser DBF nativo opcional, semanticamente equivalente ao caminho Python e integrado ao staging existente.

**Architecture:** Um crate/pacote Maturin em `native/omnisus-db-dbf` entrega lotes Arrow. Adaptadores Python/Rust compartilham integridade, normalização, staging e publicação. A API de ingestão permanece compatível.

**Tech Stack:** Python 3.12+, Rust stable, PyO3, arrow-rs/arrow-pyarrow, Maturin, dbfread2, pytest, Hypothesis, proptest, cargo-fuzz, DuckDB/DuckLake.

**Spec:** `docs/superpowers/specs/2026-09-10-rust-dbf-design.md`.

**Status:** Tarefas 1–7 implementadas e verificadas localmente em 2026-09-10.
Rust continua opt-in; a execução da matriz externa de CI e a publicação não
integram a conclusão local. Ver [evidências e comandos](../../../reports/rust-dbf-validation.md).

## Global Constraints

- Python `>=3.12`; manter o backend Hatchling do pacote principal.
- Preservar mínimos existentes: DuckDB `>=1.5.5,<2.0`, Polars `>=1.44.2,<2.0`, PyArrow `>=25.0.1`, datasus-dbc `>=0.1.3,<1.0`, dbfread2 `>=0.1.0,<2.0`.
- Extensão opcional; a instalação base não adiciona nova exigência de Cargo.
- API pública de ingestão e contratos de `Lake` permanecem compatíveis.
- `BATCH_ROWS = 100_000` continua definido somente no Python e é passado ao Rust.
- Uma implementação compartilhada de normalização, schema, IPC e Parquet.
- Nenhuma conversão de inteiro para float para acomodar valores incompatíveis.
- Nenhum fallback após começar a consumir registros do backend escolhido.
- Nenhum novo paralelismo de escrita, download ou parsing de escopos.
- A memória ainda inclui DBC e DBF completos; não prometer memória constante.
- PRs usam fixtures locais; DATASUS ao vivo fica fora dos checks obrigatórios.
- Publicação de pacotes é uma etapa posterior, sujeita à infraestrutura existente.

## Mapa, dependências e método

Ler o mapa completo de arquivos na spec §4 antes de executar. Módulos existentes
`parse.py`, `staging.py` e `_runner.py` ficam na mesma pasta. O pacote nativo usa
seu próprio `pyproject.toml`, não altera o backend de build raiz.

Dependências: 1 → 2 → 3 → 4 → 5 → 6 → 7. A execução isolou leitor, CI e
benchmark em frentes com revisão cruzada; a entrega foi consolidada no checkout
principal, preservando o trabalho concorrente nos notebooks. Os títulos de
commit abaixo são sugestões de organização, não um registro de commits feitos. Para cada comportamento novo: teste que
falha pelo motivo esperado → implementação mínima → teste verde → refatoração.
Testes de caracterização da implementação existente devem passar desde o início.
Os blocos abaixo preservam os contratos e exemplos do planejamento. Os testes
implementados podem usar nomes ou arquivos diferentes; o relatório registra os
comandos efetivamente executados. Checkboxes indicam o comportamento entregue
e validado, sem afirmar execução literal de cada comando ilustrativo.
